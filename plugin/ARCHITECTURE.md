# STE Assistant — техническое описание

Плагин STE Slicer 7.10 (форк Cura 3.6, встроенный Python 3.5) с ИИ-ассистентом печати. Пользователь пишет задачу
и прикладывает модель детали, ТЗ и фото узла. Ассистент разбирает файлы, задаёт вопросы двумя карточками —
условия работы, затем «как сделать» с рекомендацией по каждому выбору, — показывает план печати (материал, режим
3D или 5D, положение и настройки с причинами) и после подтверждения нарезает в STE Slicer и сохраняет проект 3MF и G-code.

**Порядок работы** (`plan.py`): файлы → вопросы «Условия работы» → вопросы «Как сделать» → план печати →
«Подтвердить и нарезать» → нарезка. До подтверждения в слайсере меняется только положение модели в сцене: материал и настройки туда не
пишутся, нарезки нет — ни по кнопке паспорта, ни по вызову LLM.

**Главный принцип: решения принимают правила, а не языковая модель.** Материал, режим, положение и значения
настроек считаются детерминированно — одни и те же файлы дают один и тот же результат. LLM понимает свободный
текст и фото, превращает их в требования, вызывает инструменты и объясняет результат. Без LLM весь путь
проходит автопилот на тех же правилах.

## 1. Компоненты

```
 Браузер (SPA)  ──HTTP + токен сессии──▶  Плагин STE Assistant  ──HTTPS──▶  LLM (OpenAI-совместимый API)
   чат, паспорт,     длинный опрос        сервер · агент · правила
   картотека         событий                  │
                                              │ callLater → главный поток Qt
 Внешний MCP-клиент ──POST /mcp, Bearer──▶    ▼
                                         STE Slicer: сцена, настройки, нарезка, запись файлов
```

| Модуль | Что делает |
|---|---|
| `geometry.py` | Разбор сетки из сцены через trimesh STE Slicer (ось, отверстие, устойчивые положения), нависания и силуэт на numpy |
| `spec_reader.py`, `requirements.py` | Текст ТЗ из DOCX/TXT и требования из текста |
| `images.py` | Подготовка фото для LLM |
| `materials.py`, `data/materials.json` | Профили материалов STE Slicer + файл данных со свойствами, которых в профилях нет |
| `rules.py` | Правила: материал, режим, положение, настройки, варианты печати |
| `workflow.py` | Конвейер подготовки детали: модель, требования, вопросы, материал, режим, положение, настройки, сохранение, автопилот; возврат модели детали в сцену. Остальные части сценария вынесены в модули ниже и доступны через `workflow` по-прежнему |
| `params.py` | Параметры печати из STE Slicer: правка пользователем, «Вернуть исходные», проверка сочетаний, поиск по всем настройкам |
| `slicing.py` | Нарезка, итоги, оценка времени, разбор ошибок слайсера, три варианта печати |
| `history.py` | «Было → стало»: копия состояния до правки, отмена (последние 15), вариант и значение из паспорта |
| `passport.py` | Паспорт печати, итоговый текст и подсказки после хода |
| `experience.py` | Опыт прошлых печатей из картотеки: исправления по материалу и режиму — в план новой детали |
| `review.py` | Разбор напечатанной детали по фото: каталог дефектов, ответ модели для фото, исправления параметров |
| `plan.py` | Порядок работы: вопросы в два раунда, план печати, правка плана, подтверждение |
| `agent.py`, `tools.py`, `llm.py` | Агент, 22 инструмента (в том числе `list_slicer_settings`, `reset_settings`), клиент LLM |
| `bridge_slicer.py` | Мост к API STE Slicer: сцена, профили материалов, настройки и их проверка, ModelChecker, нарезка, запись файлов |
| `server.py`, `store.py`, `catalog.py`, `mcp.py`, `web/` | Чат, хранение деталей, картотека, MCP |

Сторонних зависимостей нет: стандартная библиотека Python и то, что входит в состав слайсера, — Uranium, PyQt5,
numpy, trimesh. Если trimesh или нужных ему пакетов (scipy, networkx, rtree) в сборке нет, соответствующий шаг
разбора геометрии выполняется на numpy; в ходе работы видно, что именно посчитал trimesh.

**Всё, что умеет слайсер, плагин берёт у него** через `bridge_slicer.py`:

| Что | API STE Slicer |
|---|---|
| Загрузка, сцена, габарит, «вне рабочей зоны» | `readLocalFile`, `SceneNode.getBoundingBox`, `isOutsideBuildArea` |
| Сетка для разбора и силуэта | `MeshData.getVertices / getIndices`, `getWorldTransformation` → trimesh |
| Поворот, укладка, «положить плашмя», копии | `RotateOperation`, `TranslateOperation`, `LayFlatOperation`, `MultiplyObjectsJob`, `arrangeAll` |
| Какие материалы есть у принтера, плотность, инструкция по прилипанию | `MaterialManager.getAvailableMaterialsForMachineExtruder`, запасной путь — `ContainerRegistry.findInstanceContainersMetadata(type="material")` |
| Материал и профиль качества | `MachineManager.setMaterialById`, `setQualityGroupByQualityType` |
| Значения, подписи и описания параметров (ru_RU), пределы, варианты | стек настроек `getProperty` (value, label, description, unit, minimum_value, maximum_value, options, enabled), `i18nCatalog` |
| Все параметры для поиска «Все настройки STE Slicer» | `DefinitionContainer.findDefinitions()` глобального стека, раздел — верхний предок определения; правки пользователя — `userChanges.getInstance` |
| Проверка значений | `getProperty(key, "validationState")` — то же, что подсвечивает `MachineErrorChecker` |
| Риск коробления | плагин `ModelChecker` |
| Нарезка, время, расход | `Backend.forceSlice`, сигналы бэкенда, `PrintInformation` |
| Запись проекта и G-code | `3MFWriter`, `GCodeWriter` |

## 2. Входные файлы

Принимаются до 10 файлов в сообщении: модель STL, OBJ, 3MF (до 100 МБ), ТЗ DOCX, TXT и фото JPG, PNG (до 20 МБ).
Если моделей или ТЗ несколько, берётся последний приложенный файл.

### 2.1. Модель детали

1. **Загрузка.** Файл открывает сам STE Slicer своим штатным загрузчиком (`readLocalFile`), поэтому годится любой
   формат, который он читает. Прежние модели из сцены убираются: одна деталь — одна сцена.
2. **Сетка.** Из узла сцены берутся вершины и мировая матрица, треугольники переводятся в координаты сцены
   (Y вверх, стол — плоскость XZ). Анализ идёт по тому, что реально лежит в слайсере, а не по исходному файлу.
3. **Разбор** (`geometry.analyze`: сетка → trimesh из состава STE Slicer, недостающее — numpy):
   - габариты, объём, площадь поверхности, средняя толщина стенки (2 × объём / площадь);
   - **6 вариантов положения**: каждая грань габарита по очереди вниз; для каждого — площадь нависаний круче 45°
     и площадь опоры на столе. Устойчивость — из `trimesh.poses.compute_stable_poses`: положение, в котором
     деталь стоит с вероятностью меньше 2 %, уходит в конец списка;
   - **ось вращения**: кандидат — `symmetry_axis` trimesh. trimesh судит по моментам инерции, поэтому квадратный
     брусок для него тоже «тело вращения»; круглость проверяется по этой оси: деталь режется на 20 слоёв, в каждом
     слое считается максимальный радиус в 12 секторах; разброс меньше 6 % — тело вращения. Без trimesh так
     проверяются все три оси;
   - **сквозное отверстие**: луч вдоль оси через центр не задевает сетку (`ray.intersects_any`); диаметр —
     минимальный радиус точек от оси (больше 1 мм). Без лучей trimesh — точки на этом радиусе идут не меньше
     чем по 80 % длины детали;
   - **тонкостенная оболочка**: объём меньше 25 % от сплошного цилиндра того же габарита и стенка тоньше 4 мм
     (пыльник, гофра);
   - **нависания в 5D**: «вверх» — от оси наружу; считаются грани, смотрящие к оси под углом круче 45°.
   - **силуэт для карточки** (`geometry.silhouette`): треугольники проецируются на плоскость — тело вращения сбоку,
     осью вверх, остальное спереди — и закрашиваются построчно в сетке 128 клеток; получается путь SVG,
     ось рисуется пунктиром, сквозное отверстие — двумя тонкими линиями.
4. **Тип детали**: тело вращения со сквозным отверстием, тонкостенная оболочка вращения, сплошное тело вращения
   или деталь общей формы. Дополнительно: «лежит на боку» (ось не вертикальна), «плоская» (высота меньше четверти
   ширины).
5. **Проверки**: «вне рабочей зоны» сообщает сам слайсер (`isOutsideBuildArea`); если модель больше стола или
   меньше 3 мм — предупреждение о единицах измерения в файле.

### 2.2. ТЗ (DOCX, TXT)

1. **Текст.** DOCX разбирается как zip с `word/document.xml` без сторонних библиотек; DTD и сущности запрещены,
   размер ограничен 40 МБ. TXT читается как есть.
2. **Название и количество**: строка «Наименование детали: …» (сокращается до 2–3 слов) и «партия из N»,
   «N шт.».
3. **Требования** (`requirements.extract`). Словарь из 36 свойств — общий язык для ТЗ, правил, LLM и базы
   материалов: нагрузки (трение, износ, удар, усталость, ползучесть, жёсткость, гибкость), среда (масла, бензин,
   дизель, кислоты, щёлочи, спирт, гидролиз, УФ, озон, влага), чистота (без следов, пыли, летучих веществ,
   абразивного и проводящего наполнителя), точность, температуры и числовые пороги.
   - Текст режется на предложения; каждое проверяется регулярными выражениями свойств. У каждого свойства задан
     вид: **обязательно**, **запрещено** или **желательно**.
   - Обязательное становится желательным, если в том же предложении есть «желательно», «по возможности»,
     «допускается».
   - Числа: рабочая температура (максимум из строк про среду и режим), пиковая (капли, расплав, кратковременно),
     температура Вика и стеклования, модуль упругости, плотность, водопоглощение; запас под износ в мм.
   - У требования сохраняется цитата и номер пункта ТЗ — они видны в карточке «Требования».
   - Противоречия снимаются: гибкость против жёсткости, скольжение против высокого трения.
4. **Уточнение моделью.** LLM читает тот же текст и может вызвать `set_requirements` с тегами из того же словаря:
   добавить то, что не поймали ключевые слова, или поправить вид требования. Требования модели и ключевых слов
   сливаются, при совпадении свойства побеждает модель.

### 2.3. Фото узла (JPG, PNG)

- Фото уменьшается до 1280 px по длинной стороне, пересжимается в JPEG и передаётся в LLM как data-URL
  (`image_url`). В одном сообщении — до 3 фото, каждое до 4 МБ.
- Если основная модель не видит картинки, в настройках указывается **модель для фото**: она описывает фото
  текстом, а основная модель получает это описание. Если сервер отклонил запрос с фото, ход повторяется без них,
  и пользователь видит подсказку.
- В историю диалога фото не сохраняется — только его описание.
- По инструкции модель называет, что увидела на фото (узел, среда, сопряжённые детали), и передаёт условия работы
  в требования. Без LLM фото не анализируется.
- **Фото напечатанной детали** (`review.py`) — отдельный режим: модель для фото отвечает JSON по каталогу из 11 дефектов
  (`clear`, `question`, `defects [{id, confidence, where}]`). Непонятное фото — вопрос пользователю и выбор дефекта
  кнопками; без LLM — только кнопки и слова из сообщения. Исправления — шаги от текущих значений STE Slicer в пределах
  профиля материала; в 5D без каймы и поддержек на столе; применяются той же правкой, что в паспорте.

### 2.4. Слова пользователя и вопросы

- **Название чата** (`store.name_from_text`, `short_name`): из ТЗ, иначе из слов пользователя («Нужно напечатать
  ведущее колесо конвейерной ленты, 4 шт.» → «Ведущее колесо конвейерной ленты»; «напечатай шестерню» →
  «Шестерня»), иначе из имени файла (транслит `koleso_dlya_konveyera_v3` → «Колесо для конвейера», без `v3`,
  `final`). Фраза до 5 слов и 34 символов не обрезается; длиннее — по целым словам, но не на прилагательном
  без существительного и не на предлоге. Название, заданное пользователем, ассистент не меняет.
- Из текста сообщения без LLM извлекаются: названный материал (PETG, PA6, TPU D70…), количество («15 шт.»,
  «×15»), вариант («быстро», «дешевле», «качественно»), режим («5D», «3D»), «без поддержек» и требования тем же
  извлекателем, что и для ТЗ.
- **Вопросы в два раунда** (`plan.questions_for`). Ассистент не решает молча: где есть выбор, он спрашивает и
  предлагает рекомендацию правил (отметка «рекомендую»). У вариантов — пояснение, что изменится.
  1. **Условия работы** (`conditions_for`), только то, чего нет в ТЗ и словах:
     - «Где будет работать деталь?» — если требований нет: «В помещении, без нагрузки», «Нагрузка и удары»,
       «На улице, солнце», «Масло или топливо», «Гибкая деталь»; можно несколько;
     - «Насколько прочной должна быть деталь?» — Обычная / Повышенная / Максимальная, если ТЗ не задаёт нагрузку;
     - «Приоритетные параметры поверхности» — Внешний вид / Точные размеры / Не важно; рекомендация по ТЗ
       (декоративная деталь — вид, допуски — размеры). У прочности и поверхности рекомендованный вариант
       выбран сразу — его можно просто подтвердить;
     - «Что важнее?» — Быстро / Дёшево / Качественно, если вариант не назван.
  2. **Как сделать** (`how_for`), после ответов:
     - «Какой материал взять?» — до трёх материалов (выбранный правилами и ближайшие), у каждого — описание
       простыми словами и что из ТЗ он не проходит;
     - «Печатать в 3D или в 5D?» — если деталь можно надеть на оправку (см. 3.2), с нависаниями в обоих режимах;
     - «Как положить деталь на стол?» — три лучших положения с нависаниями, опорой и высотой;
     - «Как быть с поддержками?» — Везде / Только от стола / Без поддержек, если они нужны;
     - «Сколько штук нужно?» — последним, после режима: в 5D на оправке печатается одна деталь за запуск.
       Если деталь уже идёт в 5D, вопроса нет; если режим выбирают в той же карточке, при 5D вместо счётчика
       подсказка «для партии выберите 3D». Не спрашивается, если количество названо словами или задано ТЗ.
  Пустой раунд пропускается. Ответить можно кнопками или своими словами; «Пропустить» и «Оставить
  рекомендованное» — то, что написано в «По умолчанию — …».
- Без ответа на «Где будет работать» — **EnduSe PETG** и заполнение 40 %; оба помечаются в плане и паспорте как допущения.
- Порядок источников без ТЗ: слова → фото → имя файла → геометрия → картотека → значения по умолчанию.

## 3. Подбор параметров

### 3.1. Материал

- **Профили STE Slicer**: перед подбором плагин спрашивает у слайсера, какие материалы есть у текущего принтера
  и сопла, и берёт из профиля плотность, название и инструкцию по прилипанию. Материал без профиля в подбор не идёт.
- **Файл данных** `data/materials.json`: свойства, которых в профилях нет, — 22 материала линеек EnduSe, FiberPart,
  Sealant и Proto. `id` совпадает с `root_material_id` профиля. У каждого — флаги свойств и числа: рабочая и пиковая
  температура, Вика, стеклование, модуль, водопоглощение. Источник флага помечен: **профиль** (прямо сказано в
  описании материала в STE Slicer) или **справочник** (свойство базового полимера); профиль важнее.
- **Проверка**: каждое требование против каждого материала даёт «да», «нет» или «нет данных».
- **Рейтинг** (по возрастанию):
  1. штраф = 4 × число нарушенных обязательных требований и запретов + число «нет данных» по ним;
  2. число нарушений;
  3. больше выполненных желательных;
  4. больше подтверждённых профилем;
  5. функциональные линейки раньше прототипной Proto.
- Матрица «требование × материал» показывает выбранный материал и следующие по рейтингу. Если все нарушают ТЗ,
  берётся ближайший, и пользователь видит предупреждение.
- Материал, названный пользователем, ставится как есть, но проверяется по ТЗ; нарушения показываются и попадают
  в паспорт.
- **Простыми словами**: у каждого материала в `materials.json` есть `plain` — что это за пластик, на что похож,
  чего боится и для чего (написано по описаниям профилей Stereotech). Оно показывается в вопросе о материале,
  в строке «Материал» плана и под таблицей требований, а LLM получает его в состоянии детали.
- `profile` в `materials.json` — температура сопла и стола, обдув, откат и скорость из профиля материала STE Slicer:
  план показывает их строкой «Профиль материала», но не меняет.
- В слайсере материал ставится через `MachineManager.setMaterialById`, и плагин проверяет, что профиль
  применился. Температуры, скорости и охлаждение берутся из профиля материала Stereotech.

### 3.2. Режим 3D / 5D и база

Как устроен 5D в STE Slicer (по исходникам `CuraEngineBackend/StartSliceJob.py`, `CLIParserBackend/StartSliceJob.py`,
`Utils/GenerateBasementJob.py`): ось 5D — вертикальная ось сцены в центре стола. Слайсер режет модель цилиндром
диаметра `cylindrical_mode_base_diameter`: в `cylindrical_full` часть внутри цилиндра печатается обычными слоями,
а на оправку (`non_printing_base_diameter`, 6 мм) наматывается подложка `cylindrical_raft` до диаметра базы;
в `cylindrical` подложки нет, а всё внутри базы **вырезается и не печатается**.

Поэтому 5D подходит только детали, которую можно надеть на оправку:

| Условие | Режим | База 5D |
|---|---|---|
| Тело вращения со сквозным пустым каналом по оси Ø ≥ 8 мм, в 5D нависаний меньше половины от лучшего 3D (или в 5D их почти нет, а в 3D ≥ 100 мм²) | 5D `cylindrical_full` | диаметр канала (отверстия) |
| То же, но нависания в 5D и 3D близки | 3D, а для гибкой детали — 5D; выбор задаётся пользователю вопросом | диаметр канала |
| Тело вращения без канала, деталь общей формы | 3D `classic` | — |

- **Канал** (`geometry.free_core`) — расстояние от оси до ближайшего треугольника: каждый треугольник проецируется
  поперёк оси, и если проекция накрывает ось, канала нет. Считается по треугольникам, а не по вершинам, поэтому
  торцевая крышка без вершины в центре канал закрывает.
- Режим `cylindrical` автоматически не выбирается: он вырезает середину детали и печатает без подложки.
- 5D по просьбе пользователя для детали без канала — `cylindrical_full` с базой 6 мм и предупреждением, что часть
  внутри базы напечатается обычными слоями.
- Сравнение идёт с **лучшим** положением в 3D. В карточке «3D или 5D» видны нависания, поддержки, направление
  слоёв и база.

### 3.3. Положение на столе

- Положения считаются по разбору модели **в позе файла** (`geo_file`), а поворот делается от текущей позы
  (матрица `pose`) к выбранной: повторный выбор не накапливает повороты.
- **5D**: ось детали вертикально, деталь в центре стола — ось совпадает с осью оправки.
- **3D**: из 6 граней габарита «вниз» выбирается та, у которой есть опора на столе (≥ 50 мм²), меньше всего
  нависаний и больше площадь опоры; при равенстве деталь остаётся как в файле. Пользователь выбирает из трёх
  лучших во втором раунде вопросов или в строке плана «Положение».
- **Нависание** — грань, отклонённая от вертикали круче `support_angle` (50°, как в STE Slicer):
  cos(угла между нормалью и «вниз») > sin(50°). Грани у стола (выше него меньше 0,3 мм) не считаются.

### 3.4. Настройки слайсера

За основу берётся профиль принтера Hybrid 530 и материала Stereotech. Плагин меняет только ключевые параметры
(`rules.plan_settings`) и записывает их в пользовательский слой стека (`userChanges`), с учётом того, какие
настройки задаются на экструдер.

| Параметр | Правило |
|---|---|
| Режим, база 5D | `printing_mode`, `cylindrical_mode_base_diameter`, `cylindrical_raft_enabled` — из п. 3.2 |
| Стенки `wall_line_count` | оболочка: стенка целиком периметрами (толщина / 0,4 мм, не меньше 2); запас под износ из ТЗ: износ / 0,4 + 1, не меньше 4; прочность «максимальная»: 5; нагрузка из ТЗ или «повышенная»: 4; декоративная: 2, с тонкими элементами 3; иначе 3; «дёшево» — на линию меньше, если не задано ТЗ |
| Верх и низ `top_bottom_thickness` | 1,0 мм; нагрузка или «повышенная»: 1,2 мм; «максимальная»: 1,6 мм |
| Заполнение `infill_sparse_density` | оболочка: 100 %; крутящий момент, ползучесть, модуль или жёсткость с ударом: 100 %; циклическое сжатие с трением или точностью: 90 % (допущение); «максимальная»: 100 %; «повышенная»: 50 %; ограничение по массе: 30 %; декоративная: 15 %; нагрузка без уточнений: 40 %; требований нет: 40 % (допущение); иначе 20 % |
| Рисунок `infill_pattern` | ≥ 90 %: линии; гибкий материал: гироид; нагрузка: кубы; «быстро»: линии; иначе сетка |
| Поддержки | 3D: включены, если нависаний в текущем положении ≥ 150 мм²; у полых деталей (материал < 30 % объёма) — только от стола; `support_angle` 50°; «внешний вид» или «качественно» — слой между поддержкой и деталью (`support_interface_enable`). 5D: `support_enable` и `support_enable_cylindrical`, если в 5D остаются нависания ≥ 150 мм². Ответ «без поддержек» выключает их |
| Прилипание | PP: кайма 8 мм; «точные размеры»: юбка и компенсация первого слоя `xy_offset_layer_0` = −0,1 мм; малая опора (< 400 мм²), высокая, плоская или крупная деталь из усадочного материала: кайма 5 мм; иначе юбка. 5D: подложку на оправке строит слайсер, `adhesion_type` не пишется |
| Шов `z_seam_type` | «внешний вид» или декоративная деталь: в углах, у тел вращения — сзади одной линией |
| Слой `layer_height` | «качественно» 0,1 мм (декоративная — 0,06 мм), «дёшево» 0,15 мм, «быстро» 0,2 мм; в 5D то же в `cylindrical_layer_height` |
| Профиль материала | температура, обдув, откат, скорость — из профиля, только показываются |

- **Сброс прежних значений**: при новой записи плагин убирает из `userChanges` то, что записывал раньше, а в новом
  плане не задано (`reset_settings`), — иначе, например, кайма или база от прошлого режима остались бы в слайсере.
- **Треугольник приоритетов**: вариант можно задать точкой внутри треугольника «быстро — дёшево — качественно» (`rules.blend`): слой и множитель заполнения — взвешенное среднее вершин, остальные правила — по ближайшей вершине.
- **Варианты печати** «быстро» и «дёшево» меняют слой и уменьшают заполнение в 0,8 и 0,66 раза, но только там, где
  заполнение не задано ТЗ.
- **Закреплено ТЗ**: материал, база 5D, стенки и заполнение, которых требует ТЗ, во всех вариантах одинаковые и в
  плане не меняются кнопкой.
- **Источник** каждого параметра виден в паспорте: по ТЗ, ваш выбор, геометрия, правила, по умолчанию,
  допущение, профиль материала.
- **Проверка слайсером**: после записи плагин спрашивает у STE Slicer состояние проверки каждого изменённого
  параметра (`validationState`). Значение, которое слайсер считает ошибкой, возвращается к прежнему, а в чате
  видно, какой параметр, почему и какой предел (подпись и пределы — из определений настроек).
- **Коробление**: после настроек плагин спрашивает плагин `ModelChecker` слайсера; если тот предупреждает,
  в чате — «Риск коробления» и что помогает.
- **Партия**: копии делает и расставляет сам слайсер; только в 3D, потому что в 5D на оправке печатается одна
  деталь. Сколько копий помещается на стол за раз, оценивает `rules.per_plate` (сетка с зазором 10 мм по центру
  стола; у круглого стола Hybrid — внутри эллипса). Если партия больше, на стол ставится столько, сколько
  помещается, а план пишет число запусков: лишние копии слайсер оставил бы за рабочей зоной и не нарезал.
  Прежние копии перед новой расстановкой убираются (`remove_copies`).

### 3.4.1. Опыт прошлых печатей

Картотека помнит, что пошло не так. Когда в разборе по фото нажимают «Применить исправления», в запись
сохранённой детали попадают сами исправления (`lessons`: параметр, было, стало, дефект), а запись получает
отметку «Были проблемы». Если пользователь отметил «Были проблемы» сам и описал словами («по углам
отклеилась»), дефекты узнаются по заметке, а исправления считаются от настроек, с которыми деталь печатали.

При подборе настроек новой детали (`experience.py`, вызов в `apply_settings`) берутся записи с тем же
материалом и режимом (3D или 5D), по одному уроку на параметр, свежая запись важнее. Значение ставится, только
если правила ещё не дошли до исправления: поток был 100 → 95, правила дают 100 — ставим 95, правила уже дают
90 — не трогаем. У строки источник «опыт» и причина: «Опыт: на «Колесо» из этого материала было
«переэкструзия» — сразу ставлю 95». В чат — одна строка «Учёл опыт прошлых печатей…». Требования ТЗ и выбор
пользователя главнее опыта. Своя запись детали не учитывается.

### 3.5. План печати и подтверждение

- **План** (`plan.build`): материал, режим, положение, вариант печати, количество (в 3D) и настройки из п. 3.4 —
  стенки, верх и низ, заполнение и его рисунок, поддержки, прилипание, шов, слой, профиль материала. У каждой строки — значение и «почему», у допущений —
  слово «Допущение». Предупреждения: материал нарушает ТЗ, ни один материал не проходит,
  риск коробления крупной детали, недопустимые и рискованные сочетания параметров.
- **Сочетания с кнопкой исправления** (`rules.combo_warnings`, 14 правил): несколько штук в 5D, 5D без канала,
  разглаживание или спираль в 5D, слой толще 3/4 сопла, пустая оболочка, поддержки выключены при больших
  нависаниях, нет каймы у усаживающегося пластика, сопло далеко от профиля, холодный стол, сильный обдув, быстрый
  гибкий пластик, длинный откат. У каждого предупреждения — `id` и одно-два готовых исправления: параметры
  («Откат 3 мм», «Добавить кайму»), режим («Печатать в 3D») или количество («Оставить 1 шт.»). Кнопки есть в
  плане, в паспорте и в сообщении чата после правки — пока такое сочетание действительно есть. Нажатие
  (`params.apply_fix`) проверяет сочетания заново и идёт через те же инструменты, что правка словами: до
  подтверждения меняет план, после — пишет в STE Slicer, перенарезает и показывает «было → стало» с отменой.
- **Правка**: материал (ближайшие по рейтингу), режим 3D/5D, положение, вариант, количество и каждая настройка
  с вариантами (кроме закреплённых ТЗ) меняются кнопкой в строке; остальное — словами («материал PETG», «печатай в 3D», «5 штук»). План
  пересобирается в той же карточке, изменённые строки отмечены точкой. «Почему этот материал» и «почему 5D»
  раскрывают таблицу требований и сравнение режимов прямо в плане.
- **Подтверждение** — кнопка в плане или в паспорте, «да» или «нарежь» в чате, `confirm_plan` у LLM:
  материал ставится в слайсер, делаются копии, пишутся настройки с проверкой слайсером, затем нарезка.

## 4. Нарезка и результат

- **Запуск**. Плагин ждёт, пока сцена и настройки перестанут меняться, и запускает нарезку. Если нарезку
  сбросило поздним изменением, она перезапускается. Пределы: 300 с в 3D и 1200 с в 5D; без сигналов от
  слайсера — 120 и 240 с.
- **Результат засчитывается, только если слайсер вернул время печати, расход и G-code.** Из ответа слайсера
  берутся время по типам линий, граммы и метры; стоимость = граммы × цена за кг из настроек (по умолчанию
  3000 ₽).
- **Ошибка нарезки** переводится в причину и шаги исправления: не помещается в рабочую зону, ошибка настроек,
  материал несовместим с соплом, нарезка зависла или не началась. Параметры печати в этом случае не
  показываются: они не проверены.
- **Три варианта** («Покажи варианты») считаются тремя пробными нарезками с настоящими временем, массой и
  ценой. Применение варианта показывает таблицу «было → стало», её можно отменить.
- **Отмена**. Каждая карточка «было → стало» хранит копию состояния детали до правки — без текста ТЗ и
  значений слайсера: их не меняет правка или они читаются заново. Копии есть только у последних 15
  карточек, у более давних отмена недоступна («Давнее»). Во время хода деталь записывается на диск не чаще
  раза в 2 с, в конце хода — всегда.
- **Прогресс**. Слайсер, особенно в 5D, присылает прогресс редко, поэтому полоса идёт по оценке времени: прошлые
  нарезки запоминаются в секундах на см³ для каждого режима.

## 5. Сохранение и картотека

- Проект 3MF и G-code пишутся штатными писателями STE Slicer. Запись идёт из рабочего потока, потому что они
  сами переходят в главный поток, и вызов из главного потока ждал бы сам себя. Файл пишется во временный
  `*.part` и переименовывается после успеха.
- Имя файла собирается по шаблону из настроек: деталь, режим, материал, слой, заполнение, стенки, принтер, копии.
- В картотеку пишется запись: настройки, требования, материал, итоги нарезки и путь к модели. Поиск
  (`catalog_search`) — по словам в имени, материале, режиме и заметке. Запись можно открыть снова или взять
  как шаблон для новой детали.

## 6. Роль LLM

Подходит любой OpenAI-совместимый API; по умолчанию `https://api.timeweb.ai/v1` и `dashscope/qwen3.8-flash`.
Ключ вводится в настройках, хранится в Preferences слайсера и не попадает ни в исходники, ни в браузер.

**Ручка одна — `POST {url}/chat/completions`**, заголовок `Authorization: Bearer <ключ>`:
`model`, `messages`, `tools` (20 инструментов), `tool_choice: "auto"`, `temperature 0.2`, `max_tokens 1800`.
Ещё три вида вызова: итоговое объяснение (без инструментов), описание фото моделью для фото и проверка
подключения в настройках.

**Цикл на одно сообщение** (`agent._llm_turn`):

1. Системный промпт — роль, порядок работы и правила ответа — плюс текущее состояние детали (до 4000 символов):
   файлы, геометрия, требования, материал, режим, настройки, итоги. Модель видит актуальное состояние, а не
   держит его в памяти.
2. История — последние 24 сообщения; фото — только в текущем ходе.
3. `tool_calls` → `tools.execute` → результат в сжатом JSON как `role: tool` → снова к модели. Не больше 15
   вызовов.
4. Ответ без вызовов — текст в чат. Если модель не запустила подготовку, а модель детали приложена, плагин
   запускает её сам.
5. Временный сбой (ответ 429 или 5xx, обрыв связи) — до двух повторов с паузой 1,5 и 4 с; если сервер
   прислал `Retry-After`, пауза по нему, но не дольше 10 с. Таймаут и ошибки ключа или адреса не повторяются.
6. Нет ключа, сети или ошибка LLM после повторов — тот же путь проходит автопилот на правилах.

Главный инструмент — `prepare_part`: загрузка, разбор, вопросы двумя карточками и план печати за один вызов,
с материалом, режимом, вариантом, количеством и требованиями из слов. Режет только `confirm_plan` — после
подтверждения пользователем. Пока план не подтверждён, инструменты правки (материал, режим, вариант,
количество, настройки, требования) меняют план, а `slice` и `show_variants` отвечают «план не подтверждён». Остальные инструменты — точечные правки: требования, материал, режим,
настройки, поворот, «положить плашмя» (`LayFlatOperation`), копии, варианты, отмена, сохранение, поиск в
картотеке. Перед тем как объяснять параметр, модель вызывает `explain_setting` и цитирует подпись и описание
из определений STE Slicer, а не придумывает их. У модели есть `ask_user` (вопрос с
вариантами), у MCP-клиентов — `load_file` (приложить файл по пути).

## 7. Взаимодействие компонентов

- **Слайсер ↔ плагин.** Агент работает в своём потоке. Каждое обращение к сцене или настройкам — короткая функция в
  главном потоке Qt через `Application.callLater`; рабочий поток ждёт её с таймаутом. Окно слайсера не замирает.
  Нарезка отслеживается сигналами бэкенда: состояние, прогресс, ошибка, оценка времени.
- **Браузер ↔ плагин.** Меню «AI Assistant» открывает `http://localhost:<порт>/?t=<токен сессии>`. Все
  `/api/*` идут с заголовком `X-Session-Token`. Изменения приходят длинным опросом `GET /api/events?since=N`.
  По событию браузер забирает деталь и заменяет в ленте только изменившиеся сообщения: остальные узлы
  не мигают и не теряют раскрытые карточки. Сообщение, в котором трогали виджет или поле, перерисовывается
  при следующем обновлении всегда — на экране остаётся то, что в слайсере.
  Файлы загружаются отдельным запросом, сообщение ссылается на них по `id`. Полный список — в `API.md`.
- **MCP.** `POST /mcp`, JSON-RPC 2.0 (`initialize`, `ping`, `tools/list`, `tools/call`). По умолчанию выключен;
  когда включён — только localhost и токен Bearer. Вызовы видны в чате с пометкой «внешний клиент».
- **Хранение.** Деталь — это JSON с перепиской, паспортом и состоянием в папке данных плагина, файлы лежат рядом.
  После перезапуска всё восстанавливается.

## 8. Безопасность и проверка

- Сервер слушает только `127.0.0.1`, статика отдаётся только из `web/`, размеры тел и загрузок ограничены, DOCX
  читается без DTD и сущностей, ключ LLM не уходит в браузер.
- `python -m unittest discover -s tests` — 96 тестов: сквозной сценарий на имитации слайсера, сервер и защита,
  MCP, фото и разбор по фото, SSL, повтор запросов к LLM, мост к слайсеру на заглушках Uranium. Совместимость
  с Python 3.5 проверяется `vermin`.
- `CHECKLIST.md` — ручная проверка в настоящем STE Slicer: то, что заглушки не покрывают.
- `tests/e2e/smoke.js` (его же запускает `tests/test_ui.py`) — проверка в браузере через Playwright на
  `tools/dev_server.py`: модель → вопросы → план → нарезка → правка в паспорте → отмена → ширина 360 px, без
  ошибок в консоли. Без Node.js или Playwright тест пропускается.
